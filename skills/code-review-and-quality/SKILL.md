# Code Review and Quality（代码审查与质量）

## Overview（概述）

多维度代码审查与质量门。每个更改在合并前都要审查——没有例外。审查涵盖五个轴：correctness、readability、architecture、security 和 performance。

**批准标准：** 当更改确实改善了整体代码健康时批准，即使它不完美。完美的代码不存在——目标是持续改进。不要因为更改不完全是你写的那样就阻止它。如果它改善了代码库并遵循项目约定，批准它。

## When to Use（何时使用）

- 合并任何 PR 或更改前
- 完成功能实现后
- 当另一个 agent 或模型产出了你需要评估的代码时
- 重构现有代码时
- 任何 Bug 修复后（审查修复和回归测试）

## The Five-Axis Review（五轴审查）

### 1. Correctness（正确性）

代码是否做了它声称做的事？

- 是否符合 spec 或任务要求？
- 边界情况是否处理（null、empty、边界值）？
- 错误路径是否处理（不只是 happy path）？
- 是否通过所有测试？测试是否真的测了正确的东西？
- 是否有 off-by-one 错误、race conditions 或状态不一致？

### 2. Readability & Simplicity（可读性与简洁性）

另一个工程师（或 agent）能否在作者不解释的情况下理解这段代码？

- 名称是否具有描述性并与项目约定一致？（没有 `temp`、`data`、`result` 脱离上下文）
- 控制流是否直接（避免嵌套三元运算符、深层回调）？
- 代码是否逻辑组织（相关代码分组、清晰的模块边界）？
- 是否有任何应该简化的"聪明"技巧？
- **能否用更少的行数完成？**（1000 行能 100 行完成就是失败）
- **抽象是否值得其复杂性？**（第三次用例前不要泛化）

### 3. Architecture（架构）

更改是否符合系统设计？

- 遵循现有模式还是引入新模式？如果是新的，是否有正当理由？
- 是否保持干净的模块边界？
- 是否有应该共享的代码重复？
- 依赖是否流向正确方向（无循环依赖）？
- 抽象级别是否适当（不过度工程化、不过度耦合）？

### 4. Security（安全性）

详细安全指南参见 `security-and-hardening`。更改是否引入了漏洞？

- 用户输入是否经过验证和清理？
- Secrets 是否远离代码、日志和版本控制？
- 需要的地方是否检查了 authentication/authorization？
- SQL 查询是否参数化（无字符串拼接）？
- 输出是否编码以防止 XSS？
- 依赖是否来自可信来源且没有已知漏洞？

### 5. Performance（性能）

详细 profiling 和优化参见 `performance-optimization`。更改是否引入了性能问题？

- 任何 N+1 查询模式？
- 任何无界循环或不受约束的数据获取？
- 任何应该 async 的同步操作？
- UI 组件中任何不必要的 re-renders？
- list endpoints 上缺少分页？
- hot paths 中创建的大对象？

## Change Sizing（更改大小）

小而聚焦的更改更容易审查、更快合并、更安全部署。瞄准这些大小：

```
~100 行更改   → 好。一次审查完。
~300 行更改   → 可接受如果是单一逻辑更改。
~1000 行更改  → 太大。拆分它。
```

**什么算"一个更改"：** 单一的、自包含的修改，解决一件事，包含相关测试，提交后系统保持功能。一个功能的一部分——不是整个功能。

**将重构与功能工作分开。** 重构现有代码并添加新行为的更改是两个更改——分别提交。

## Review Process（审查流程）

### Step 1: Understand the Context（理解上下文）

看代码前，理解意图：这个更改试图完成什么？它实现了什么 spec 或任务？

### Step 2: Review the Tests First（先审查测试）

测试揭示意图和覆盖范围：测试是否存在？它们测的是行为（而非实现细节）吗？边界情况覆盖了吗？

### Step 3: Review the Implementation（审查实现）

用五轴思维遍历代码。

### Step 4: Categorize Findings（分类发现）

用 severity 标记每条评论：

| 前缀 | 含义 | 作者行动 |
|--------|---------|---------------|
| *(无前缀)* | 必需更改 | 合并前必须处理 |
| **Critical:** | 阻塞合并 | 安全漏洞、数据丢失、功能损坏 |
| **Nit:** | 次要，可选 | 作者可以忽略——格式化、风格偏好 |
| **Optional:** / **Consider:** | 建议 | 值得考虑但不是必需的 |
| **FYI** | 仅信息 | 无需行动——为未来参考提供上下文 |

### Step 5: Verify the Verification（验证验证）

检查作者的验证故事：运行了什么测试？构建通过了吗？手动验证了吗？UI 更改有截图吗？

## Multi-Model Review Pattern（多模型审查模式）

使用不同模型进行不同审查视角：

```
Model A 编写代码
    │
    ▼
Model B 审查正确性和架构
    │
    ▼
Model A 处理反馈
    │
    ▼
Human 做最终决定
```

这捕获了单一模型可能遗漏的问题——不同模型有不同的盲点。

## Dead Code Hygiene（死代码卫生）

任何重构或实现更改后，检查孤儿代码：

1. 识别现在不可达或未使用的代码
2. 显式列出它
3. **删除前询问：** "我应该移除这些现在未使用的元素吗：[list]?"

## Review Speed（审查速度）

慢审查阻塞整个团队。上下文切换的成本小于强加给他人的等待成本。

- **一个工作日内响应**——这是最大值，不是目标
- **大型更改：** 要求作者拆分，而非审查一个巨大的 changeset

## Handling Disagreements（处理分歧）

解决审查争议时，应用此层级：

1. **技术事实和数据** 覆盖意见和偏好
2. **Style guides** 是风格问题的绝对权威
3. **Software design** 必须基于工程原则评估，而非个人偏好
4. **Codebase consistency** 可接受如果它不降低整体健康

**不要接受"我稍后会清理"。** 经验表明延迟清理很少发生。要求清理在提交前完成。

## The Review Checklist（审查检查清单）

```markdown
## Review: [PR/Change title]

### Context
- [ ] 我理解这个更改做什么以及为什么

### Correctness
- [ ] 更改符合 spec/任务要求
- [ ] 边界情况已处理
- [ ] 错误路径已处理
- [ ] 测试充分覆盖更改

### Readability
- [ ] 名称清晰一致
- [ ] 逻辑直接
- [ ] 没有不必要的复杂性

### Architecture
- [ ] 遵循现有模式
- [ ] 没有不必要的耦合或依赖
- [ ] 抽象级别适当

### Security
- [ ] 代码中没有 secrets
- [ ] 边界处输入已验证
- [ ] 没有注入漏洞
- [ ] 已进行 auth 检查

### Performance
- [ ] 没有 N+1 模式
- [ ] 没有无界操作
- [ ] list endpoints 有分页

### Verification
- [ ] 测试通过
- [ ] 构建成功
- [ ] 手动验证完成（如适用）

### Verdict
- [ ] **Approve** — 准备合并
- [ ] **Request changes** — 必须解决问题
```

## Red Flags（危险信号）

- PR 未经任何审查就合并
- 审查只检查测试是否通过（忽略其他轴）
- 没有实际审查证据的 "LGTM"
- 安全敏感更改没有安全聚焦审查
- 太大而无法适当审查的大型 PR（拆分它们）
- Bug 修复 PR 没有回归测试
- 没有 severity 标签的审查评论——不清楚什么是必需的 vs 可选
- 接受"我稍后会修复"——它永远不会发生
