description: 通过用户访谈创建包含微小 commits 的详细重构计划，然后将其作为 GitHub issue 提交。当用户想规划重构、创建重构 RFC，或将重构拆分为安全的增量步骤时使用。
---

当用户想创建重构请求时，将调用本 skill。你应该执行下面的步骤。如果你认为某些步骤不必要，可以跳过。

1. 请用户详细描述他们想解决的问题以及任何潜在的解决方案想法。

2. 探索仓库以验证他们的断言并了解代码库的当前状态。

3. 询问他们是否考虑过其他选项，并向他们展示其他选项。

4. 就实现访谈用户。要极其详细和彻底。

5. 敲定实现的精确范围。确定你计划改变什么和不改变什么。

6. 在代码库中检查该区域的测试覆盖。如果测试覆盖不足，询问用户的测试计划。

7. 将实现拆分为微小 commits 的计划。记住 Martin Fowler 的建议："使每个重构步骤尽可能小，以便你总能看到程序在正常工作。"

8. 用重构计划创建一个 GitHub issue。对 issue 描述使用以下模板：

<refactor-plan-template>

## Problem Statement（问题陈述）

开发者面临的问题，从开发者的视角描述。

## Solution（解决方案）

问题的解决方案，从开发者的视角描述。

## Commits（Commits）

一个详尽的、详细的实现计划。用平实英文写计划，将实现拆分为尽可能小的 commits。每个 commit 都应该让代码库处于可工作状态。

## Decision Document（决策文档）

已做出的实现决策列表。可以包括：

- 将要构建/修改的模块
- 将要修改的模块接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们可能很快过时。

## Testing Decisions（测试决策）

已做出的测试决策列表。包括：

- 什么是好的测试的描述（只测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似类型的测试）

## Out of Scope（范围之外）

对本重构范围之外的事项的描述。

## Further Notes (optional)（进一步说明）（可选）

关于重构的任何其他说明。

</refactor-plan-template>
