本 skill 获取当前对话上下文和对代码库的理解来生成 PRD。不要面试用户——直接综合你已知道的内容。

issue 追踪器和分类标签词汇应该已经提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

## Process（流程）

1. 探索仓库以了解代码库的当前状态（如果尚未这样做）。在整个 PRD 中使用项目的领域词汇表词汇，并尊重你正在修改区域的任何 ADR。

2. 勾勒出完成实现所需构建或修改的主要模块。积极寻找可以提取的 deep modules（深层模块），这些模块可以独立测试。

一个 deep module（与 shallow module 相对）是将大量功能封装在一个简单、可测试的接口中，且很少变化的模块。

与用户确认这些模块是否符合他们的预期。询问用户他们希望为哪些模块编写测试。

3. 使用以下模板编写 PRD，然后发布到项目 issue 追踪器。应用 `ready-for-agent` 分类标签——无需额外分类。

<prd-template>

## Problem Statement（问题陈述）

用户所面临的问题，从用户的视角描述。

## Solution（解决方案）

问题的解决方案，从用户的视角描述。

## User Stories（用户故事）

一个详尽的、编号列表形式的用户故事。每个用户故事应采用以下格式：

1. 作为一个 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为一名移动银行客户，我想要查看账户余额，以便对我的支出做出更明智的决定
</user-story-example>

这个用户故事列表应该非常详尽，涵盖该功能的各个方面。

## Implementation Decisions（实现决策）

已做出的实现决策列表。可以包括：

- 将要构建/修改的模块
- 将要修改的模块接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们可能很快过时。

例外：如果原型产生的片段能比散文更精确地编码一个决策（状态机、reducer、schema、类型形状），将其内联到相关决策中，并简要注明它来自原型。修剪到决策丰富的部分——不是可工作的演示，只是关键部分。

## Testing Decisions（测试决策）

已做出的测试决策列表。包括：

- 什么是好的测试的描述（只测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似类型的测试）

## Out of Scope（范围之外）

对本 PRD 范围之外的事项的描述。

## Further Notes（进一步说明）

关于该功能的任何其他说明。

</prd-template>
