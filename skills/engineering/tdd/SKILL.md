# Test-Driven Development（测试驱动开发）

## Philosophy（哲学）

**核心原则**：测试应该通过公共接口验证行为，而非实现细节。代码可以完全改变；测试不应该。

**好的测试**是集成风格的：它们通过公共 API 演练真实的代码路径。它们描述系统*做什么*，而非*怎么做*。一个好的测试读起来像规范——"用户可以用有效购物车结账"准确地告诉你存在什么能力。这些测试能在重构中存活，因为它们不关心内部结构。

**坏的测试**与实现耦合。它们模拟内部协作者、测试私有方法，或通过外部手段验证（如直接查询数据库而非使用接口）。警告信号：你重构时测试失败了，但行为没变。如果你重命名了一个内部函数而测试失败，那些测试就是在测实现，而非行为。

示例和模拟指南参见 [tests.md](tests.md) 和 [mocking.md](mocking.md)。

## Anti-Pattern: Horizontal Slices（反模式：水平切片）

**不要先写所有测试，再写所有实现。** 这是"水平切片"——把 RED 当作"写所有测试"，GREEN 当作"写所有代码"。

这会产生**垃圾测试**：

- 批量编写的测试测的是*想象的*行为，而非*实际的*行为
- 你最终测的是事物的*形状*（数据结构、函数签名）而非用户面向的行为
- 测试对真实变化不敏感——行为损坏时它们通过，行为正常时它们失败
- 你超出了你的车灯范围，在理解实现之前就承诺了测试结构

**正确方法**：通过 tracer bullets（示踪弹）进行垂直切片。一个测试 → 一个实现 → 重复。每个测试都回应你从上一次循环中学到的东西。因为你刚写了代码，你确切知道什么行为重要以及如何验证。

```
WRONG (horizontal):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

RIGHT (vertical):
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## Workflow（工作流）

### 1. Planning（规划）

在探索代码库时，使用项目的领域词汇表，使测试名称和接口词汇与项目语言匹配，并尊重你正在修改区域的 ADR。

在写任何代码之前：

- [ ] 与用户确认需要哪些接口变更
- [ ] 与用户确认要测试哪些行为（按优先级）
- [ ] 识别 [deep modules](deep-modules.md) 的机会（小接口，深实现）
- [ ] 为[可测试性](interface-design.md)设计接口
- [ ] 列出要测试的行为（而非实现步骤）
- [ ] 获得用户对计划的批准

问："公共接口应该长什么样？哪些行为最重要需要测试？"

**你无法测试所有内容。** 与用户确认哪些行为最重要。将测试精力集中在关键路径和复杂逻辑上，而非每个可能的边界情况。

### 2. Tracer Bullet（示踪弹）

写一个测试来确认系统的一个行为：

```
RED:   为第一个行为写测试 → 测试失败
GREEN: 写最小代码让它通过 → 测试通过
```

这是你的示踪弹——证明端到端路径可行。

### 3. Incremental Loop（增量循环）

对于每个剩余行为：

```
RED:   写下一个测试 → 失败
GREEN: 最小代码让它通过 → 通过
```

规则：

- 一次一个测试
- 仅够让当前测试通过的代码
- 不要预判未来的测试
- 保持测试聚焦在可观察的行为上

### 4. Refactor（重构）

在所有测试通过后，寻找[重构候选](refactoring.md)：

- [ ] 提取重复
- [ ] 深化模块（将复杂性藏在简单接口后面）
- [ ] 在合适的地方应用 SOLID 原则
- [ ] 考虑新代码揭示了现有代码的什么
- [ ] 每次重构步骤后运行测试

**永远不要在 RED 时重构。** 先到达 GREEN。

## Checklist Per Cycle（每轮检查清单）

```
[ ] 测试描述行为，而非实现
[ ] 测试仅使用公共接口
[ ] 测试能在内部重构中存活
[ ] 代码对当前测试是最小的
[ ] 没有添加投机性功能
```
