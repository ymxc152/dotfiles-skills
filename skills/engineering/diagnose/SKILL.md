# Diagnose（诊断）

针对顽固 Bug 的纪律性流程。仅在明确有理由时才跳过某些阶段。

在探索代码库时，使用项目的领域词汇表来构建相关模块的清晰心智模型，并查阅你正在修改区域的 ADR。

## 阶段 1 — 构建反馈循环

**这就是本 skill 的核心。** 其余都是机械操作。如果你有一个快速、确定性、可由 agent 运行的通过/失败信号来验证 Bug，你就能找到原因——二分查找、假设测试和插桩都只是消耗这个信号。如果你没有这样的信号，再多的代码审视也救不了你。

在这里投入不成比例的努力。**要激进。要有创造力。绝不放弃。**

### 构建反馈循环的方法 — 大致按此顺序尝试

1. **失败的测试** — 在能触及 Bug 的任意接缝处：单元、集成、e2e。
2. **Curl / HTTP 脚本** — 针对运行的开发服务器。
3. **CLI 调用** — 使用固定输入，将 stdout 与已知的正确快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）— 驱动 UI，断言 DOM/控制台/网络。
5. **重放捕获的 trace。** 将真实的网络请求/负载/事件日志保存到磁盘；在隔离环境中重放它。
6. **临时 harness。** 启动系统的最小子集（一个服务，模拟依赖），用单次函数调用触发 Bug 代码路径。
7. **属性 / 模糊测试循环。** 如果 Bug 是"有时输出错误"，运行 1000 次随机输入并寻找失败模式。
8. **二分 harness。** 如果 Bug 出现在两个已知状态之间（commit、数据集、版本），自动化"在状态 X 启动，检查，重复"，以便你可以 `git bisect run`。
9. **差异循环。** 在旧版本 vs 新版本（或两种配置）中运行相同输入并 diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人类点击，用 `scripts/hitl-loop.template.sh` 驱动*他们*，使循环仍然结构化。捕获的输出反馈给你。

构建正确的反馈循环，Bug 就解决了 90%。

### 迭代优化循环本身

把循环当作产品来对待。一旦你有了*一个*循环，问自己：

- 能让它更快吗？（缓存设置，跳过无关初始化，缩小测试范围。）
- 能让信号更尖锐吗？（断言具体症状，而非"没崩溃"。）
- 能让它更确定吗？（固定时间，固定随机种子，隔离文件系统，冻结网络。）

一个 30 秒的不稳定循环几乎等于没有循环。一个 2 秒的确定性循环是调试超能力。

### 非确定性 Bug

目标不是干净的复现，而是**更高的复现率**。循环触发 100 次，并行化，增加压力，缩小时间窗口，注入睡眠。50% 抖动的 Bug 是可调试的；1% 不是——不断提高复现率直到可调试。

### 当你真的无法构建循环时

明确停止并说明。列出你尝试过的方法。向用户请求：(a) 访问能复现它的环境，(b) 捕获的工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 允许添加临时生产环境插桩。在**没有循环的情况下不要继续假设**。

在有了可信的循环之前，不要进入阶段 2。

## 阶段 2 — 复现

运行循环。观察 Bug 出现。

确认：

- [ ] 循环产生的失败模式是**用户**描述的——而不是附近碰巧出现的另一种失败。错误的 Bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或者，对于非确定性 Bug，复现率足够高以进行调试）。
- [ ] 你已捕获确切的症状（错误消息、错误输出、慢速时间），以便后续阶段可以验证修复是否真的解决了它。

在复现 Bug 之前不要继续。

## 阶段 3 — 假设

在测试任何一个假设之前，先生成**3–5 个排序后的假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：陈述它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 Bug 消失 / <改变 Z> 会让它更严重。"

如果你无法陈述预测，这个假设只是直觉——丢弃或 sharpen 它。

**在测试前向用户展示排序后的列表。** 他们通常拥有能立即重新排序的领域知识（"我们刚部署了对 #3 的更改"），或知道他们已经排除的假设。廉价的检查点，巨大的时间节省。不要阻塞——如果用户 AFK，继续按你的排序进行。

## 阶段 4 — 插桩

每个探针必须映射到阶段 3 中的具体预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查** — 如果环境支持。一个断点胜过十个日志。
2. **定向日志** — 在能区分假设的边界处。
3. 永远不要"记录所有内容然后 grep"。

**给每个调试日志加上唯一前缀标记**，例如 `[DEBUG-a4f2]`。最后清理时只需一次 grep 即可。未标记的日志会存活下来；标记的日志必须被删除。

**性能分支。** 对于性能回归，日志通常是错误的。相反：建立基准测量（时间 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，再修复。

## 阶段 5 — 修复 + 回归测试

**在修复之前**编写回归测试——但前提是存在**正确的接缝**。

正确的接缝是指测试能在调用点演练**真实的 Bug 模式**。如果唯一可用的接缝太浅（单调用者测试当 Bug 需要多调用者，单元测试无法复现触发 Bug 的链），那里的回归测试会给人虚假信心。

**如果不存在正确的接缝，这本身就是发现。** 记录下来。代码库架构正在阻止 Bug 被锁定。标记到下一阶段。

如果存在正确的接缝：

1. 将最小化后的复现转换为该接缝处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始（未最小化的）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 事后分析

在宣布完成之前必须：

- [ ] 原始复现不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或接缝缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 临时原型已删除（或移动到明确标记的调试位置）
- [ ] 最终正确的假设在 commit / PR 消息中陈述——以便下一个调试者学习

**然后问：什么能预防这个 Bug？** 如果答案涉及架构变更（没有好的测试接缝、纠缠的调用者、隐藏的耦合），将具体情况交给 `/improve-codebase-architecture` skill。在修复**之后**提出建议，而非之前——你现在比开始时拥有更多信息。
