# Prototype（原型）

原型是**回答问题的可丢弃代码**。问题决定形状。

## Pick a branch（选择分支）

确定正在回答哪个问题——从用户的提示、周围代码中，或如果用户在附近则通过询问：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个微小的交互式终端应用，将状态机推过在纸上难以推理的情况。
- **"这个应该长什么样？"** → [UI.md](UI.md)。在单个路由上生成几种截然不同的 UI 变体，可通过 URL search param 和浮动底部栏切换。

两个分支产生非常不同的产物——选错了会浪费整个原型。如果问题确实模糊且用户无法联系，默认选择与周围代码更匹配的分支（后端模块 → logic；页面或组件 → UI），并在原型顶部陈述假设。

## Rules that apply to both（两者都适用的规则）

1. **从一开始就是可丢弃的，并明确标记为如此。** 将原型代码放在它实际将被使用的地方附近（紧挨着它原型的模块或页面），这样上下文很明显——但命名它时要让随意阅读者能看出它是原型，而非生产代码。对于可丢弃的 UI 路由，遵守项目已有的路由约定；不要发明新的顶层结构。
2. **一条命令运行。** 无论项目现有的 task runner 支持什么——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能够不假思索地启动它。
3. **默认无持久化。** 状态存在于内存中。持久化是原型正在*检查*的东西，而非它应该依赖的东西。如果问题明确涉及数据库，访问一个 scratch DB 或一个带有清晰的 "PROTOTYPE — wipe me" 名称的本地文件。
4. **跳过打磨。** 没有测试，没有超出使原型*可运行*的错误处理，没有抽象。重点是快速学习然后删除。
5. **展示状态。** 每次操作（logic）或每次变体切换（UI）之后，打印或渲染完整的相应状态，以便用户能看到什么改变了。
6. **完成后删除或吸收。** 当原型回答了它的问题时，要么删除它，要么将验证过的决策折叠到真实代码中——不要让它在仓库里腐烂。

## When done（完成时）

原型中唯一值得保留的是*答案*。将它捕获到某个持久的地方（commit message、ADR、issue 或原型旁边的 `NOTES.md`），连同它回答的问题。如果用户在附近，那个捕获是一次快速对话；如果不在，留下占位符以便他们（或你，在下一次 pass 中）可以在删除原型之前填写 verdict。
